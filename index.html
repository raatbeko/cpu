Почему ядра, а не частота

Закон Мура говорит о транзисторах: их число на кристалле удваивается примерно каждые два года. До середины 2000-х это давало и рост тактовой частоты, и однопоточная программа ускорялась сама, без усилий программиста.

Около 2004 года частота упёрлась в стену. Потребляемая мощность растёт быстрее частоты, и кристалл на 5 ГГц нельзя охладить обычным воздухом. Транзисторы продолжают дешеветь, но тратятся теперь на новые ядра, кэш и векторные блоки.

Отсюда главный вывод раздела: программа, которая использует одно ядро, на новом процессоре почти не быстрее, чем на старом. Чтобы использовать современный процессор, программа должна быть параллельной.

Классификация Флинна

Майкл Флинн в 1966 году предложил делить вычислительные системы по двум признакам: сколько потоков команд и сколько потоков данных они обрабатывают одновременно. Получается четыре класса. На схемах синим текут команды, коричневым данные. Наведите на класс, чтобы рассмотреть его поближе.

Закон Амдала

В любой программе есть часть, которую нельзя распараллелить: чтение входа, инициализация, слияние результатов. Обозначим её долю f. Джин Амдал в 1967 году заметил, что именно она ограничивает ускорение, сколько бы процессоров ни было.

S(p) = 1 / (f + (1 − f) / p),   S(∞) = 1 / f

Подвигайте ползунки. Полоса ниже показывает время программы: коричневая часть последовательная и не сжимается, синяя параллельная и делится на число ядер. Справа — сами ядра: видно, сколько из них реально работает.

Закон Густафсона

Джон Густафсон в 1988 году возразил: на практике, получив больше процессоров, люди не решают ту же задачу быстрее, а решают задачу побольше за то же время. Прогноз погоды считают не за минуту вместо часа, а с более мелкой сеткой за тот же час.

S(p) = p − f · (p − 1)

Тогда последовательная часть остаётся прежней, а параллельная растёт вместе с числом ядер, и ускорение почти линейно. Законы не противоречат друг другу: они описывают разные ситуации, которые называют сильным и слабым масштабированием.

Метрики: эксперимент на ваших ядрах

Теория проверяется замером. Ускорение S = T₁ / Tₚ, эффективность E = S / p. Есть и обратная метрика Карпа–Флэтта: по замеренному ускорению она восстанавливает последовательную долю. Если она постоянна, мешает последовательный код; если растёт с числом потоков, мешают накладные расходы или нехватка ядер.

Что ждать. Пока потоков не больше, чем ядер, ускорение растёт почти линейно, а Карп–Флэтт держится около нуля. Как только потоков становится больше ядер, время перестаёт падать, а Карп–Флэтт резко растёт: это не последовательный код, это потоки делят одни и те же ядра. На дорожках это видно: полосы ползут рывками.
Почему числа скачут. Браузер делит ядра с другими вкладками и системой, а ноутбуки снижают частоту под нагрузкой. Поэтому каждая точка — медиана из трёх запусков, и первый запуск делается «вхолостую» для прогрева JIT.

Как это записывается на Java

Потоки Java выполняются как потоки операционной системы на разных ядрах, поэтому именно на Java удобно проверять законы этого раздела. Три способа разложить одну и ту же сумму на ядра, от явного к декларативному.

Ядро вычисления

static double kernel(long from, long to, double h) {
    double sum = 0.0;
    for (long i = from; i < to; i++) {
        double x = (i + 0.5) * h;
        sum += 4.0 / (1.0 + x * x);
    }
    return sum;
}

Одна и та же функция во всех вариантах, иначе JIT скомпилирует их по-разному, и сравнение будет нечестным.

// диапазон делится на p равных блоков
try (var pool = Executors.newFixedThreadPool(p)) {
    List<Future<Double>> parts = new ArrayList<>();
    for (int k = 0; k < p; k++) {
        long from = n * k / p, to = n * (k + 1) / p;
        parts.add(pool.submit(() -> kernel(from, to, h)));
    }
    double sum = 0;
    for (var f : parts) sum += f.get();
    return sum * h;
}

Явный контроль: видно, где создаются потоки и где собираются результаты. Потоки не пишут в общие переменные, гонок нет.

protected Double compute() {
    if (to - from <= THRESHOLD)
        return kernel(from, to, h);
    long mid = (from + to) >>> 1;
    var left = new SumTask(from, mid, h);
    left.fork();              // в очередь
    double right = new SumTask(mid, to, h).compute();
    return right + left.join();
}

Рекурсивное деление пополам. Свободные потоки забирают задачи из чужих очередей (work-stealing), нагрузка выравнивается сама.

return LongStream.range(0, n).parallel()
    .mapToDouble(i -> {
        double x = (i + 0.5) * h;
        return 4.0 / (1.0 + x * x);
    })
    .sum() * h;

Самая короткая запись. Внутри тот же ForkJoinPool, но число потоков задаётся общим пулом, а не программой.
